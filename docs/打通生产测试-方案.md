# 打通生产测试 — 方案（Bambuddy 集成测试工具链）

> 状态：Phase 1–4 已落地（2026-07-31），生产采集已完成。本文档是「打通生产测试」的完整方案，供另一台开发机/服务器恢复与继续。
> 关联代码：`backend/tools/`（recorder / schema / capture / canary）＋ `backend/tests/`（fixtures corpus ＋ 生命周期驱动测试）。

## 一、背景与目标

原来的测试鸿沟：

- **dev 只测得出 200、生产才有 bug**：本地 Bambuddy Docker（v0.2.4.9）与生产（v1.2.5.1）版本差巨大，行为/字段不一致。
- **真打印一次 3–10 分钟**：没法作为日常回归手段，也没法覆盖失败/取消分支。
- 每次改 adapter/poller/dispatch，都只能靠"上生产盯着"验证。

目标：**不碰生产写入，也能拿生产形态数据**；让 dev 后端跑"生产形态数据"、秒级走完完整订单生命周期，并在生产侧放一个只读安全网。

## 二、核心原则

1. **只读硬守卫**：所有采集/canary 工具只允许 `GET`，永不 import 任何写方法（`stop_print` / `add_to_queue` / `cancel_queue_item` / `remove_queue_item` / `upload_archive` / debug 钩子均不在路径内）。
2. **版本差异交给 adapter 兼容层**：生产 v1.2.5.1 vs dev v0.2.4.9 字段结构有差异，但 adapter 已完全兼容（实测契约测试对 prod 全绿）。
3. **合成事件可驱动真实核心**：3DFarm 状态机两个输入（poller 拉 + webhook 推）收敛到 `services/bambuddy_sync.py::apply_event`，合成事件即可瞬时驱动完整状态机 + credit 联动，无需物理打印。

## 三、工具链（backend/tools/ + backend/tests/）

| 工具 | 职责 |
|---|---|
| `tools/bambuddy_recorder.py` | record / replay / fault / sequence 四模式代理。路径规范化把数字 id 段模板化为 `{id}`，dev（VP id 1）与 prod（P1S id 2）采集通用。pytest 用 conftest 的 `replay_proxy` fixture（函数级、port=0、teardown 还原 `BAMBUDDY_BASE_URL`）。 |
| `tools/bambuddy_schema.py` | 校验 poller / dispatch / webhook 消费的字段；`logical_path()` 路径规范化。 |
| `tools/capture_bambuddy.py` | 只读 GET 采集 CLI → `tests/fixtures/bambuddy/{live,prod}/`。 |
| `tools/canary.py` | 生产只读冒烟，GET-only 守卫，退出码驱动告警（0=全过 / 1=有错误或不可达）。 |
| `tests/conftest.py` | `replay_proxy` / `point_bambuddy` / `make_ready_order`（走真实事件核心到 READY_TO_PRINT 并绑 job）等 fixture。 |
| fixture corpus | `tests/fixtures/bambuddy/{live, prod, seq_print, seq_printers_sync}/` |
| 测试 | `test_bambuddy_fixtures.py`（契约）、`test_lifecycle_webhook.py`（合成事件走真实核心）、`test_lifecycle_poller.py`（replay 喂序列 4 次 `_do_sync` 走完 READY_TO_PRINT→PRINT_COMPLETED＋capture、AMS 克数富化、500 注入不崩）、`test_bambuddy_sync.py`（补全 webhook/poller 分支）。 |

## 四、打通路径（现状）

1. **生产形态数据获取**：dev 开发机可**直接直连生产 Bambuddy NAT 端点** `http://172.25.56.19:18000`（Bambuddy 内部 8000 被映射到该端口），无需再上 .83 采集。已从 dev 完成生产采集 → `tests/fixtures/bambuddy/prod/`（生产 v1.2.5.1 真实数据：4 台真机 BME-112-B/C/D/E、id 1–4；14 个料盘分配含 `weight_used`；9 条真实队列项）。
   ```bash
   # 采集命令（dev 直连生产，只读 GET）
   python tools/capture_bambuddy.py --base-url http://172.25.56.19:18000 \
       --printer-id <真机id> --out tests/fixtures/bambuddy/prod [--api-key <若有>]
   ```
2. **契约测试对 prod 全绿**：`test_bambuddy_fixtures.py` 用真实生产响应断言 schema/adapter 解析，生产格式变了立刻红。
3. **canary 对生产只读冒烟**：`tools/canary.py --base-url http://172.25.56.19:18000`（或 .83 对 .19 的映射地址）已对生产验证 **13 checks exit 0**——health、printers、virtual-printers、queue、inventory/assignments + 每台真机 status / inventory-remain，逐个跑 schema 校验，非 2xx 或校验错计入 errors，退出码 1。
   ```bash
   python tools/canary.py --base-url http://172.25.56.19:18000 [--api-key KEY] [--out canary.log]
   ```
4. **生命周期秒级驱动**：webhook 合成事件直接喂 `apply_event`；poller 用 `seq_print` 序列 replay 喂 4 次 `_do_sync`。两种输入都可在秒级把订单走完 READY_TO_PRINT→PRINT_COMPLETED＋credit 结算，且覆盖失败/取消分支。
5. **版本差异实证**：生产 v1.2.5.1 vs 本地 dev Docker v0.2.4.9——版本差巨大但 adapter 完全兼容；BME-112-C 真实 `state=FAILED` 且 `hms_errors=[]` → 映射 IDLE（"FAILED 假象"真实案例）。

## 五、剩余打通步骤（待办）

1. **canary 定时部署**（未做）：Windows 任务计划程序每 15 分钟跑 `canary.py`，退出码驱动告警；部署在 dev 机或 .83 服务器均可。生产格式一漂移（schema drift / 连通性）就能提前预警。
2. **可选真打印采集完整生命周期 + 真实 webhook payload**（未做）：在极小模型上启动一次真实打印，采集从 `print_started` 到 `complete` 的完整 webhook payload，替换当前合成的 seq_print 序列。**需用户授权在生产启动一次打印**（生产写入操作），此前保持只读不碰。
3. **`print_start` 映射修复待决策**（一行 + 测试）：Bambuddy 会发 `print_start` 事件，但 `EVENT_STATE_MAP` 里没有该映射 → 纯 webhook 路径下订单会卡在 READY_TO_PRINT。修法：在状态机加 `print_start → PRINTING` 映射 + 对应测试；需确认与 poller 路径是否冲突。

## 六、关键坑（开发时）

- **webhook 幂等 key 含 timestamp**：驱动序列每步必须唯一 timestamp，否则 `replayed` 不推进。
- **READY_TO_PRINT 不能直接转 PRINT_FAILED**（状态机约束）：失败分支要先 `print_started`。
- **`BambuddyAdapter(base_url=...)` 在 api_key 空时仍读 `current_app.config`** → 需 app context（测试里包 `app.app_context()`）。
- **代理回放**：fixture body 存的是已解析 JSON（list 也是），回放必须按 `body_encoding=="json"` 重新 `json.dumps`，不能 `str()`（会变 Python repr，非法 JSON）。
- 生产采集 fixture 里 `GET__printers__ID.json` 的数字 id 段是模板 `{id}`，live 与 prod 通用（dev VP id 1 / prod 真机 id 不同也能复用）。

