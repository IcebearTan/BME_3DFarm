## 1. 项目定位

### 1.1 是什么

项目代号 **BME_3DFarm**。一个**独立**的 3D 打印农场管理系统，**仅面向内网客户**（训练营学员/内部成员）。客户用 credit 额度下单打印，平台管理订单、额度、打印机调度和进度跟踪。底层通过 Bambuddy 管理 **7 台 P1S 打印机**。

### 1.2 关键决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 与 BME 训练营的关系 | **独立项目，不耦合** | 不拖累训练营稳定性；商业模型不同；独立演进；未来"联动"是两个系统对接而非内部耦合 |
| 底层打印机通信 | **用 Bambuddy（成熟开源）** | 完整 REST API + Webhook + 多打印机 + 摄像头 + Docker；BambuPrinterGateway 已完成 Phase 0 验证（证明局域网 IP+SN+授权码可连），其历史使命完成 |
| BambuPrinterGateway 去向 | 降级为**诊断工具** | 保留 `bambu-phase0` / `bambu-gateway-monitor` 用于排查硬件问题；不作为生产集成对象 |
| 业务模型 | **Credit 预付制** | 客户持有 credit，下单冻结、完成实扣、失败释放 |
| 训练营联动时机 | **以后再说，现在只留接口钩子** | 不让早期联动需求绑架架构 |
| 客户范围 | **仅内网**（训练营学员/内部） | 不做公网开放，简化安全/合规；远程访问走 VPN |
| Credit 来源 | **发放制，无支付** | 管理员发放 + 活动获取 + 训练营奖励；不做在线支付/充值 |
| 取件流程 | **不做，打完即订单完成** | 简化状态机，去掉取件/配送环节 |
| 通知渠道 | **邮件**（Flask-Mail） | 最小必要，后续按需扩展 |
| 打印机规模 | **7 台 P1S**（AMS 待逐台确认） | 决定多打印机管理 + AMS 多色支持 |

### 1.3 不做什么（YAGNI）

第一版明确不做：
- 公网开放（仅面向内网客户）
- 在线支付/充值系统（credit 仅靠发放：管理员 + 活动 + 训练营奖励）
- 取件/配送流程（打印完成即订单完成）
- 训练营奖励体系深度集成（只留 credit 发放 API 钩子）
- 服务器端自动切片（Phase 4 才考虑）
- 全自动调度（先半自动）
- 客户直接看摄像头
- 多门店/多农场（先单点）

关于上传格式：**允许 `.3mf`（模型）和 `.gcode.3mf`（已切片）两种**。内网信任场景下允许客户上传已切片的 `.gcode.3mf` 直接打印；`.3mf` 模型文件需管理员切片后才能打印（Phase 1 管理员手动用 Bambu Studio 切）。

## 2. 技术栈

**核心原则：与 BME 平台同栈，保证团队只维护一套技能、代码模式可互相复用。**

| 组件 | 选型 | 说明 |
|---|---|---|
| 后端框架 | Flask + Flask-SQLAlchemy + Flask-Migrate + Flask-JWT-Extended | 完全同 BME |
| 数据库 | MySQL 8.0 | 同 BME；credit 账务用 `SELECT FOR UPDATE` + 流水表保证正确性 |
| 缓存/队列 | Redis | broker + result backend + 限流；同 BME 用法 |
| 后台任务 | **Celery + Celery Beat** | 补齐 Flask 同步模型的异步能力，见 §2.1 |
| 前端 | Vue 3 + Element Plus + Vite + Vuex | 同 BME；复用 DewUI 设计语言 / 暗色模式 / 无 emoji 约束 |
| 对象存储 | MinIO | 存 3D 模型文件（可能数百 MB），不进数据库 |
| 部署 | Docker Compose | 单机：backend + worker + beat + redis + mysql + bambuddy + minio |

### 2.1 为什么是 Flask（同步）+ Celery，而不是 FastAPI（async）

**async 对本平台影响接近零。** async 真正发光的场景（高并发、WebSocket、MQTT 长连、流式），在本平台都被架构手段化解了：

| 场景 | 处理方式 |
|---|---|
| 高并发客户请求 | 打印有物理产能天花板（一台机日产能个位数），请求量天然上不去，同步 Flask 足够 |
| WebSocket 实时推送 | 架构绕开——客户轮询进度，不用 WS |
| MQTT 长连打印机 | Bambuddy 隔离——它自己 async 维护 MQTT，本平台只调它 HTTP |
| 调 Bambuddy 取状态 | 不在客户请求路径上——Poller 后台定时调，结果写 DB，客户读 DB |
| 长任务（切片） | 丢 Celery Worker，async 也救不了 |

结论：**Flask 同步进程只干"接 HTTP + 读写 DB"，这部分同步模型完全够。异步需求全部交给 Celery。** Redis 复用，增量运维只有 Worker 进程。

### 2.2 Celery 在本平台的定位

Celery 不是偏离同栈，恰恰是**让 Flask 同栈能撑住产品级的补全件**。Flask + Celery 是 Python 圈最成熟的组合之一。

本平台 Celery 的使用场景：

| 场景 | Phase | 强度 |
|---|---|---|
| Poller 定时同步打印机状态 | 2 | 中（Celery Beat 定时 + 内置重试） |
| Webhook 异步处理（快速 ACK + 后台处理） | 2 | 强 |
| 半自动 dispatch（上传大文件 + 加队列） | 3 | 强（不阻塞管理员请求） |
| 服务器切片 | 4 | 刚需 |
| 发通知邮件 | 全程 | 中 |

**引入策略**：Phase 0 就搭好 Celery 骨架（Redis 复用 + Worker/Beat 进程 + celery_app.py），但 task 按需写——Phase 0-1 不写业务 task，骨架空转不碍事；Phase 2 开始按需增加。这样既避免后期加部署组件，又不在早期过度设计。

## 3. 整体架构

### 3.1 架构总览

```
┌──────────────── 内网 / 局域网 ─────────────────┐
│                                                   │
│   客户前端              管理前端                    │
│  (下单/查进度/         (订单/打印机/额度/           │
│   我的额度)             审核/报表)                  │
│                                                   │
└─────────┬──────────────────┬──────────────────────┘
          │ HTTPS / JWT       │ HTTPS / JWT + RBAC
          │                   │
┌─────────▼──────────────────▼──────────────────────┐
│            打印农场后端 (Flask)                     │
│                                                    │
│  Blueprints:                                       │
│    auth / orders / credit / admin                  │
│    webhook_bambuddy / internal(预留训练营)          │
│                                                    │
│  Services:                                         │
│    CreditService / OrderStateMachine / Pricing     │
│                                                    │
│  BambuddyAdapter  ← 唯一打印机出口（接口抽象）       │
│                                                    │
│  Celery Beat ── 定时触发 ──┐                       │
└──┬──────┬──────┬──────┬────────────┼──────────────┘
   │      │      │      │            │
   ▼      ▼      ▼      ▼            ▼
 MySQL  Redis  MinIO  Celery Worker 进程
                          │
                          ▼
                    HTTP + X-API-Key
                    ┌──────────────┐
                    │   Bambuddy    │  Docker, 内网
                    │  (打印机底座)  │
                    └──────┬───────┘
                  MQTT 8883 / FTPS 990 / RTSPS 322
                           │
                    ┌──────▼───────┐
                    │  拓竹打印机×N │
                    └──────────────┘
```

### 3.2 三个通信关系（务必区分）

| 关系 | 协议 | 网络 | 模式 |
|---|---|---|---|
| 浏览器 ↔ Flask | HTTPS | 公网 | 请求-响应，JWT 认证 |
| Flask/Worker ↔ Bambuddy | HTTP + X-API-Key | **内网** | 请求-响应 |
| Bambuddy ↔ 打印机 | MQTT/FTPS/RTSPS | **内网** | 发布订阅 + 文件传输 |

**硬性边界**：
- Bambuddy 永不暴露公网
- 客户永远不直接接触 Bambuddy / 打印机 IP / SN / Access Code
- 只有 Flask 后端和 Worker 能访问 Bambuddy API

### 3.3 BambuddyAdapter 的战略意义

`BambuddyAdapter` 是本平台访问打印机的**唯一入口**，业务代码只依赖它的接口，不直接调 Bambuddy。

这是对冲 Bambuddy 风险的核心手段：万一 Bambuddy 写入 API 不够用、或项目停更，可以基于 BambuPrinterGateway 已验证的 `bambu-connect` 连接能力，自研一个精简的写入适配实现，**业务层一行不改**。

接口（随阶段递增）：
```
Phase 0 (只读):  list_printers / get_printer_status / list_queue / health_check
Phase 2 (只读+): get_archive / list_archives
Phase 3 (写入):  add_to_queue / remove_queue_item / upload_archive
Phase 3+ (控制): start_print / clear_plate
```

## 4. Credit 机制设计

### 4.1 核心原则

**额度不直接改余额，全靠流水驱动。** 每次变动写一笔 `credit_transaction`，记录前后余额快照 + 幂等键。对账 = 查流水。

### 4.2 账户模型（双余额，不是单 balance）

```
credit_account
  available_credit   可用额度（能花的）
  frozen_credit      冻结额度（下单锁住的）
  total = available + frozen
```

**绝对不要只存一个 `balance`**——否则并发下单超扣、退款说不清、失败重打追不到。

### 4.3 流水类型

```
type 枚举:
  grant      发放（管理员发放/活动获取，本平台 credit 唯一增加途径）
  freeze     下单冻结
  capture    完成实扣（冻结转实扣）
  release    失败/取消释放（冻结回可用）
  refund     退款（实扣退回账户）
  adjust     管理员手动调整（扣减/补发）
  reward     训练营奖励（给训练营联动预留，现在不用）
```

每笔流水：
```
id, user_id, order_id(可空), type, amount,
before_available, after_available,
before_frozen, after_frozen,
source(admin_grant/activity/training_camp/system),
reason, operator_id(可空),
idempotency_key(unique),
created_at
```

### 4.4 并发安全

所有额度操作：
1. `SELECT ... FOR UPDATE` 锁账户行
2. 修改 available / frozen
3. 写一笔 transaction（含前后快照）
4. 提交事务

关键操作（freeze/capture/refund）用幂等键防重：
```
freeze:idempotency_key = "freeze:{order_id}:{quote_version}"
capture:idempotency_key = "capture:{order_id}:{print_job_id}"
refund:idempotency_key = "refund:{order_id}:{reason_code}:{version}"
```

### 4.5 定价模型

```
预估 credit = 基础开机费
            + 预估耗材克重 × 材料单价
            + 预估打印小时 × 机时单价
            × 风险/加急系数
```

- **Phase 1**：人工报价，管理员审核时手填 credit 数
- **Phase 4**：自动报价，按模型体积/耗材/时间估算（依赖切片结果）

下单冻结"预估 credit"，完成按"实际 credit"多退少补（或初期固定按预估扣，简化）。

### 4.6 Credit 在订单生命周期里的流动

```
下单确认   → freeze(冻结预估)
打印完成   → capture(冻结转实扣，按实际用量)
打印失败   → release(释放冻结) 或 部分扣（按业务规则，进人工）
取消订单   → release(释放冻结)
退款       → refund(实扣退回)
```

**失败不自动扣费也不自动退款，进人工处理**——规避客诉地狱。

### 4.7 Credit 来源（本平台无支付）

credit 只通过"发放"进入系统，没有在线支付/充值入口：

| 来源 | type | source | 谁触发 |
|---|---|---|---|
| 管理员发放 | grant | admin_grant | 管理员后台 |
| 活动获取 | grant | activity | 管理员后台/活动系统 |
| 训练营奖励 | reward | training_camp | 未来训练营系统调 `POST /internal/credit/grant` |

`grant` 和 `reward` 都增加 `available_credit`，写一笔流水。`adjust` 用于纠错（可加可减）。**永远不直接改余额，只写流水**。

## 5. 数据模型

### 5.1 核心表清单（MVP 8 张）

| 表 | 用途 | Phase |
|---|---|---|
| `user` | 用户账户 | 1 |
| `credit_account` | 额度账户（双余额） | 1 |
| `credit_transaction` | 额度流水 | 1 |
| `order` | 打印订单 | 1 |
| `order_file` | 订单文件 | 1 |
| `printer` | 业务侧打印机抽象（7 台 P1S + AMS 配置） | 0 |
| `bambuddy_job` | 订单 ↔ Bambuddy 任务映射 | 2 |
| `print_event` | 打印事件（Webhook/Poller） | 2 |

> `quote`（报价）Phase 1 人工，可塞进 order 字段；Phase 4 自动报价时再独立成表。

### 5.2 关键字段

**user**
```
id, email(unique), password_hash, name, role(default/customer),
external_user_id(可空, 给训练营SSO预留), sso_subject(可空),
status, created_at, updated_at
```

**credit_account**
```
id, user_id(unique FK), available_credit(decimal),
frozen_credit(decimal), currency_type(default 'point'), updated_at
```

**credit_transaction**：见 §4.3

**order**
```
id, order_no(unique), user_id(FK),
status, public_status(脱敏),
material, color, layer_height, nozzle_size, quantity,
estimate_weight_g, estimate_print_seconds,
estimated_credit, frozen_credit, actual_credit,
priority, due_at, customer_note, admin_note,
public_progress(0-100), remaining_seconds,
created_at, updated_at
```

**order_file**
```
id, order_id(FK), file_type(source_model/sliced_file/preview),
original_filename, storage_key(MinIO), content_type,
size_bytes, sha256, version, scan_status, created_at
```

**printer**（业务侧打印机抽象，Phase 0 录入）
```
id, public_name, internal_name, bambuddy_printer_id,
model(default 'P1S'), has_ams(bool), capabilities(json),
status(idle/printing/offline/error/maintenance),
last_seen_at, enabled(bool), created_at, updated_at
```

**bambuddy_job**（订单-Bambuddy 映射，Phase 2）
```
id, order_id(FK), order_no,
bambuddy_printer_id, bambuddy_queue_id, bambuddy_archive_id,
filename, job_token(unique),
bambuddy_status, dispatched_at, started_at, completed_at,
last_sync_at, mapping_confidence(exact/filename/manual)
```

**print_event**（事件落库，Phase 2）
```
id, order_id(FK), bambuddy_job_id(FK),
source(webhook/poller/admin), event_type,
raw_payload(json), normalized_payload(json),
idempotency_key(unique), created_at
```

### 5.3 订单状态机（MVP 简化版）

```
DRAFT → FILE_UPLOADED → QUOTING → WAITING_CONFIRM → CREDIT_RESERVED
  → REVIEWING → APPROVED → READY_TO_PRINT → PRINTING
  → PRINT_COMPLETED → QC_PENDING → CLOSED

异常分支:
  REVIEWING → REJECTED → REFUNDED → CLOSED
  PRINTING → PRINT_FAILED → NEED_REVIEW → (重打 or REFUNDED)
  任意未打印状态 → CANCELLED → CLOSED
```

> 完整 20+ 状态机见 `bambuddy_customer_platform_architecture.md` §5。MVP 先用上面简化版，后续按需扩展。所有状态转换经 `OrderStateMachine` 统一处理，自动写状态变更日志。

### 5.4 客户可见状态映射

内部状态不直接暴露，映射为脱敏状态：
```
DRAFT/FILE_UPLOADED/QUOTING       → 报价中
WAITING_CONFIRM                    → 待确认
CREDIT_RESERVED/REVIEWING/APPROVED → 准备打印
READY_TO_PRINT                     → 排队中
PRINTING                           → 打印中
PRINT_COMPLETED/QC_PENDING         → 已打印，质检中
PRINT_FAILED/NEED_REVIEW           → 异常处理中
REJECTED                           → 无法打印
REFUNDED                           → 已退款
CLOSED                             → 已完成
```

## 7. 阶段实施计划

> 按阶段规划，不细排周。每个阶段有明确验收标准和 Gate。

### Phase 0 — 底座打通 + 技术验证【体量：小】

**目标**：确认 Bambuddy 能用、API 够用；搭起独立项目骨架。

**主要工作**
- Docker 部署 Bambuddy，填 BambuPrinterGateway 已验证的 IP/SN/access code 连打印机
- 在 Bambuddy API Browser **实测全部要用的接口**（见 §7.1 Gate）
- 搭 backend 骨架（Flask + MySQL + Redis + Celery 空骨架）
- 建 `bambuddy_adapter.py` 只读骨架
- 从 Flask 调通 `list_printers()` / `get_printer_status()`，确认返回字段（`gcode_state`/`mc_percent`/`mc_remaining_time` 等，与 Gateway MQTT 收到的是同一批）

**验收**：Flask 能从 Bambuddy 读到打印机实时状态；产出《Bambuddy 接口实测报告》。

**Gate（全局技术关卡）**：Bambuddy 写入 API 是否够用，决定后续产品形态——
- 够用 → Phase 3 可做半自动 dispatch
- 不够用 → 降级为"管理员手动打印 + 系统管订单/credit/状态"，Phase 3 砍调度
- **此 Gate 必须在 Phase 0 闭合**

### Phase 1 — 用户 + Credit + 订单核心（人工打印闭环）【体量：大】

**目标**：跑通"注册→充值→下单→人工打印→实扣 credit"完整商业闭环，**不碰打印机自动化**。

**主要工作**
- 用户系统：注册/登录/JWT（仿 BME auth.py）；user 表留 `external_user_id` / `sso_subject`
- Credit 系统：account + transaction + CreditService（全部 `SELECT FOR UPDATE` + 事务 + 幂等）
- 订单系统：order + order_file + OrderStateMachine（简化状态机）
- 定价：人工报价
- 内部 API `POST /internal/credit/grant`（给训练营预留）
- 前端：客户侧（登录/我的额度/下单/我的订单）+ 管理侧（订单列表/审核报价/credit管理）
- 打印机**手动**：管理员在 Bambuddy 手动打印，后台点"标记完成"触发实扣

**验收**：两账号端到端走完——管理员发放 credit、下单冻结、审核报价、确认、人工打印+标记完成、实扣；失败释放。

**风险**：credit 并发正确性，必须写并发测试。

### Phase 2 — 状态自动同步（Bambuddy 只读 + Webhook）【体量：中】

**目标**：进度/完成/失败自动同步，客户体验闭环。

**主要工作**
- `bambuddy_job` 映射表 + 文件名带 order_no
- Poller（Celery Beat 每 30s）：同步打印机状态、队列、更新活跃订单进度
- Webhook 接收器 `/internal/webhooks/bambuddy/{secret}`：落 `print_event` + 幂等处理
- 订单-Bambuddy 任务**手动绑定**
- 对账逻辑（订单状态 vs Bambuddy 状态不一致）
- 客户侧进度页接真实数据（脱敏）
- 完成通知（Flask-Mail）

**验收**：管理员手动打印后，客户进度条自动更新；打印完成自动进"已完成/待质检"；Webhook 重复发送不重复扣费。

**风险**：订单-任务绑定匹配逻辑。

### Phase 3 — 半自动调度【体量：中】

**目标**：管理员后台一键下发打印，不用去 Bambuddy UI。

**主要工作**
- 后台"分配打印机 + 下发"按钮 → Celery task 调 `adapter.add_to_queue()`
- 自动建立订单-Bambuddy 映射（archive_id 优先，filename 兜底）
- 文件进 Bambuddy archive 的方式（取决于 Phase 0 实测）
- 失败重打、取消队列项

**Gate**：依赖 Phase 0 写入 API 结论。不够则降级或跳过。

**验收**：管理员点一个按钮，文件自动进 Bambuddy 队列并开始打印，全程不切 Bambuddy UI。

### Phase 4 — 自动化与定价（按需）【体量：大】

服务器切片 / 自动报价 / 自动调度匹配材料打印机。规模化才需要，初期不做。

### 7.1 Phase 0 的 Bambuddy 接口实测清单

部署 Bambuddy 后，在 API Browser 逐一验证（这份清单是 Phase 0 的核心交付）：

**只读档（必过）**
- `GET /printers` — 返回打印机列表
- `GET /printers/{id}` — 单台详情
- `GET /printers/{id}/status` — 状态（progress/remaining_time/temperatures/hms）
- `GET /queue` — 内部队列
- `GET /archives` / `GET /archives/{id}` — 打印归档
- `GET /health` — 健康检查

**写入档（决定 Gate）**
- `POST /queue` — 加入队列（参数：archive_id + printer_id）
- `DELETE /queue/{id}` — 删除队列项
- `POST /queue/reorder` — 重排队列
- 文件如何进入 archive/library（API 上传？管理员 UI 导入？）← **最关键不确定点**

**控制档（Phase 3+ 才用）**
- `POST /printers/{id}/clear-plate` — 清板
- 打印速度/暂停等

**Webhook 配置**
- 配置 Webhook 指向测试接收器，打一次测试模型，确认 print_started/complete/failed 事件 payload 格式

每个接口记录：实际路径、参数、返回字段、是否如文档所述。**写入档任一关键接口不通 → 触发 Phase 0 Gate 降级判定。**

## 8. 风险与对策

| 风险 | 严重度 | 所在阶段 | 对策 |
|---|---|---|---|
| Bambuddy 写入 API 不够用 | 高 | Phase 0 | Gate 闭合；BambuddyAdapter 抽象层 + 自研写入兜底（复用 Gateway） |
| Credit 并发正确性（算错钱） | 高 | Phase 1 | 双余额 + 流水 + `FOR UPDATE` + 幂等键 + 专项并发测试 |
| 订单-Bambuddy 任务绑定错配 | 高 | Phase 2 | archive_id 优先 + filename 带 order_no 兜底 + 人工绑定 + 幂等 |
| Webhook 丢失/重复 | 中 | Phase 2 | Poller 兜底 + 幂等去重 + 事件落库 |
| Bambuddy 项目停更/API 破坏性变更 | 中 | 全程 | 锁版本；Adapter 隔离；自研兜底 |
| Bambu Lab 固件/协议变更 | 中 | 全程 | 无法消除的平台风险；关注 Bambuddy 更新 |
| 客户文件安全（.gcode.3mf 直打） | 低 | Phase 1 | 内网信任下允许直传 .gcode.3mf；仍做类型/大小校验 + hash；.3mf 走管理员切片 |
| 多租户隔离 | 中 | Phase 1 | 订单/文件查询全部带 user_id 过滤；MinIO 私有存储 |
| 打印机物理故障（堵头/翘边/断料） | 中 | 运营 | 人工干预入口（暂停/重打/退款）；失败进人工 |
| 7 台 P1S 的 AMS 配置不一致 | 中 | Phase 0 | 逐台确认 AMS；多色任务只分派给有 AMS 的机器 |

## 10. 部署方案

### 10.1 Docker Compose 服务

```yaml
services:
  backend:    # Flask + Gunicorn
  worker:     # celery -A celery_app worker
  beat:       # celery -A celery_app beat
  redis:      # broker + result backend
  mysql:      # 业务库
  minio:      # 模型文件
  bambuddy:   # 打印机底座，host 网络模式
```

### 10.2 网络要求

- 本平台**仅内网部署**，打印机、服务器、Bambuddy 同一局域网
- Flask 后端默认不暴露公网；客户/管理员在内网或通过 VPN/Tailscale 访问
- Bambuddy / MySQL / Redis / MinIO 仅内网可达
- 如确需公网访问（如远程管理），通过反向代理 + HTTPS + 访问控制，且 Bambuddy 仍不直接暴露

### 10.3 服务器配置建议

| 规模 | CPU | 内存 | 存储 |
|---|---|---|---|
| 1-5 台打印机 | 2 核 | 4 GB | 100 GB SSD |
| 5-20 台 | 4 核 | 8 GB | 500 GB SSD |

| # | 问题 | 决策 |
|---|---|---|

### 11.1 仍需确认：AMS 逐台配置

AMS 是拓竹的自动供料系统（选配件），4 槽位，决定该机能否多色打印。P1S 本身不含 AMS，需现场确认 7 台 P1S 各自是否加装了 AMS，记录到 `printer` 表的 `has_ams` / `capabilities` 字段。多色订单只能分派给有 AMS 的机器。
